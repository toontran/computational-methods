0. TL;DR
--------

New score, name "S6":

    u_sk(v)   = raw_sk(v)  / sk_F2_low      raw_sk = ||A_sketch v||^2
    u_g1(v)   = raw_g1(v)  / cur_F2         raw_g1 = ||A_cur v||^2
    u_g2(v)   = raw_g2(v)  / fut_F2         raw_g2 = ||A_fut v||^2

    sk_F2_low = ||A_sketch||_F^2 = sum_i s_i^2  (rank-r carry; state.s)
    cur_F2    = ||A_cur||_F^2
    fut_F2    = ||A_fut||_F^2

    score(v) = HM3(u_sk, u_g1, u_g2)         when sketch present (block ≥ 2)
    score(v) = HM2(u_g1, u_g2)               block-1 fall-through

  HM3(a,b,c) = 3 / (1/a + 1/b + 1/c);  HM2(a,b) = 2/(1/a + 1/b)

NOTE — the F-weights are matrix-Frobenius squared, NOT the existing
c_X = N_X / F2_X used by S4/S5/HM-evi. The differences:

  - sk_F2_low is the rank-r CARRY (state.s · state.V^T), not the full
    A_sk_full. It sits at ≈1.65–1.93 across blocks because s_top ≈ 0.91–0.99
    dominates. (vs sk_F2_full which grows linearly: 26 → 793.)
  - cur_F2 ≈ fut_F2 ≈ 26.4 (constant — half-window of unit-energy rows).
  - On the g-side this collapses to almost the same thing as c-weighting up
    to a per-block constant; the structural difference is on the sketch
    side: u_sk uses 1/sk_F2_low (≈0.55), c_sk · raw_sk uses N_sk/sk_F2_full
    (which scales differently with block).

Optional `· relH1(A_cur v)` factor (mirroring S4/S5) — RECOMMENDED to start
WITHOUT it, since the diagnostic shows the bare HM3 already places the
oracle at the top of the order on most blocks. Add relH1 only if streaming
underperforms.

Block-1 fall-through is HM2(u_g1, u_g2). This matches S4/S5 fall-through
(they fall to HM2(raw_g1, raw_g2)·relH1; we drop relH1 and switch to
F-weighted u_g's).

Three structural observations driving design:

  O1. Oracle is REACHABLE under F-HM3. Unlike S5 which gives oracle = 0
      score in the gate-clipped region, F-HM3 puts the oracle at rank 1 on
      4 of 5 blocks. S5's structural failure (P4 in the prior context) is
      avoided here because there's no hard gate.

  O2. oracle_v2_proj falls off a cliff at b12+ (0.0106 → 0.0025 → ...). At
      late blocks it has high u_sk (0.28→0.46) but tiny u_g1, u_g2
      (0.007→0.0017): HM3 is dominated by the smallest term and gets
      crushed. This is the new pathology.

  O3. combined_v1/v2 are always last (~1e-6). They have raw_g2 ≈ 1e-6
      because the combined-step optimizer fits A_cur + carry but is
      essentially orthogonal to A_fut. Single tiny u_g2 → tiny HM3.
      Translation: in streaming, combined's V_default[:, 1] is NOT a good
      seed for slot-2 under F-HM3.

Block-1 specific finding (verified manually, see prior message log):
  At b1, c_sk = 0 → c-weighted HM-evi reduces to HM(raw_g1, raw_g2). Since
  cur_F2 ≈ fut_F2, that's the SAME objective (up to scale) as the F-HM3
  fall-through HM(u_g1, u_g2). So c_evi_v1 is by construction the
  near-maximum of the new F-HM3 at block 1. oracle_v_proj is balanced
  but not optimal for the local-block HM. This is a feature, not a bug.


2. Gradient derivation (analytic)
---------------------------------

Let
  y_sk = A_sketch v,   y_c = A_cur v,   y_f = A_fut v
  raw_sk = y_sk·y_sk,  raw_g1 = y_c·y_c,  raw_g2 = y_f·y_f
  d raw_sk / dv = 2 A_sk^T y_sk
  d raw_g1 / dv = 2 A_c^T  y_c
  d raw_g2 / dv = 2 A_f^T  y_f

For a fixed scalar W > 0,  d (raw / W) / dv = (1/W) · d raw / dv.

HM3 case (sketch present):
  D    = 1/u_sk + 1/u_g1 + 1/u_g2
  HM3  = 3 / D
  d (1/u_X) / dv = -(1/u_X^2) · d u_X / dv = -(1/u_X^2) · (1/W_X) · (2 A_X^T y_X)
                 = -(W_X / raw_X^2) · 2 · A_X^T y_X     (since u_X = raw_X/W_X)

  d HM3 / dv = -(3/D^2) · dD/dv = (HM3^2 / 3) · (W_sk/raw_sk^2)·(2 A_sk^T y_sk)
                                 + (HM3^2 / 3) · (W_c/raw_g1^2)·(2 A_c^T y_c)
                                 + (HM3^2 / 3) · (W_f/raw_g2^2)·(2 A_f^T y_f)

  where W_sk = sk_F2_low, W_c = cur_F2, W_f = fut_F2.

  Equivalent form (the cleanest, mirroring r_sk_g_score.py:200–208):
    coef = HM3^2 / 3
    grad = coef * (1/u_sk^2) * (1/W_sk) * 2 A_sk^T y_sk
         + coef * (1/u_g1^2) * (1/W_c)  * 2 A_c^T  y_c
         + coef * (1/u_g2^2) * (1/W_f)  * 2 A_f^T  y_f

  Sign-check: positive on each term (no sketch shortfall flip — u_sk is
  "good" energy, not a penalty). Score is high when ALL three u's are big.

HM2 case (block 1, no sketch):
  D2 = 1/u_g1 + 1/u_g2
  HM2 = 2 / D2
  grad = (HM2^2 / 2) * [(1/u_g1^2)(1/W_c) 2 A_c^T y_c + (1/u_g2^2)(1/W_f) 2 A_f^T y_f]

Edge cases:
  - u_g1 ≤ eps  OR  u_g2 ≤ eps  → score := 0,  grad := 0
  - u_sk ≤ eps with sketch present (degenerate carry direction): treat as
    block-1-style fall-through OR as 0. Pick block-1 fall-through (more
    informative), but note score will jump when sketch appears.
  - sk_F2_low ≤ eps (rank-r carry empty) → no sketch case.

Numerical: prefer float64 inside the value/grad. The g-side denominators
include 1/u_g^2 = (cur_F2/raw_g1)^2 which can be 1e8+ on counterexample
candidates — fine in float64 as long as raw_g1 isn't underflowing.

6. Pitfalls
-----------

P1. (NEW for S6, NOT in prior context) — combined_v1/v2 are tail-of-the-pack
    under S6. Their raw_g2 ≈ 1e-6 makes u_g2 ≈ 4e-8 → HM3 ≈ 1e-7. Implication:
    in streaming, do NOT seed slot-2 from V_default[:, 1] alone — the
    optimizer will be at a near-zero starting point. Always include
    sketch_v[:,0/1] AND mgain_svd_v[0/1] as additional starts (these have
    decent u_sk and reasonable u_g1).

P2'. (REVISED from P2 in prior context) — Slot-1 deflation against
    V_default[:, 0] is more harmful for S6 than for S5. S6 wants v's that
    have BOTH u_sk and u_g coverage. Deflating against V_default[:, 0]
    removes the carry direction from B_search, but oracle_v1_proj at b31
    on mixed-tail-sharp has u_sk = 0.062 (the "carry-aligned" component is
    NOT V_default[:, 0]'s direction; it's spread). So deflation will damage
    S6 less than it damaged S5 — but it still removes part of the basin.

    RECOMMENDATION: try BOTH wiring variants for S6:
      (a) standard: B_search ⊥ V_default[:, 0] (current code path)
      (b) "no-deflate": run S6 over B_union for both slots, sequential
          rank-2 (use S6_v1_full / S6_v2_deflate from analyze_block).
          Slot-1 is then chosen by S6, not by combined.
    Compare on T3 — pick whichever has higher final_exact_cos[1]^2.

P3. (UNCHANGED) future_hmean_online includes an oracle-aware candidate
    (q2_vs_q1oracle). When comparing S6 to online, either drop that
    candidate from ONLINE_POOL or note the oracle dependence.

P4. (UNCHANGED) Plateau argument — any scalar-per-v score has a 62-dim
    level set in R^64 union span. S6 still has this limit; the oracle is
    NOT at the global plateau on counterexamples. The diagnostic shows
    S6 puts oracle in top 2 NUMERICALLY, but the basin can still be
    narrow. T4 (oracle-init probe) checks whether the optimizer stays
    near the oracle when seeded there.

P5. (UNCHANGED) Streaming bench final_* numbers are at block 31. For
    intermediate analysis use the rows[] in the JSON.

P6. (UNCHANGED + EXTENDED) F-norms (sk_F2_low, cur_F2, fut_F2) must be
    consistent in TWO places:
      (a) analyze_block in r_sk_g_score.py
      (b) inline in half_window_sliding_hmean_experiment.py:566+
    Compute once per block from the snapshot:
      sk_F2_low = float(np.sum(A_sketch**2))   (rank-r carry; NOT full)
      cur_F2    = float(np.sum(A_cur**2))
      fut_F2    = float(np.sum(A_fut**2))
    Do NOT mix sk_F2_full (used by per_block_constants) with sk_F2_low.

P7. (NEW) u_sk uses sk_F2_low (rank-r) but the energy budget that the
    sketch could in principle hold is sk_F2_full (linear in block_id).
    sk_F2_low is a tight cap because raw_sk ≤ s_top^2 ≈ sk_F2_low / 2 when
    s_1 ≈ s_2. So u_sk ∈ [0, 1] tightly (not loosely). Implication: u_sk's
    dynamic range is ~0.5 (capped at ≈0.5 for sketch-aligned v's), so the
    HM3 tends to be dominated by u_g terms which can be 10^-3 to 10^-2 —
    much smaller. The score is g-bottlenecked by design.


7. What NOT to do
-----------------

  - Do NOT add a hard gate on u_sk (e.g., score := 0 if u_sk < T). That
    re-introduces S5's structural failure (P4 in prior context).
  - Do NOT use sk_F2_full instead of sk_F2_low. sk_F2_full grows with
    block, so u_sk would shrink linearly with block — the score would
    become block-id sensitive in a way the rank-r carry isn't.
  - Do NOT remove relH1 from S4/S5 to make this "S6 with relH1". Keep
    S6 bare (no relH1) for the first round; experiment with relH1 only
    after T3.
  - Do NOT reuse S5's sketch-init warm-start (start = state.V[:, :2]).
    Under S6 those starts have u_g1, u_g2 ≈ 1e-5 → HM3 collapses, the
    optimizer may not escape the basin. Use mixed starts (V_default,
    mgain_svd, oracle_v_proj if --no-oracle-warmstart is off).

11. Open follow-ups (DO NOT pursue before T3 lands)
---------------------------------------------------

F1. Add relH1 factor:  score = HM3(u_sk, u_g1, u_g2) · relH1(A_cur v)
    Only if T3 sliding cos[1]² is between S5 and combined.

F2. Soft gate on u_sk:  multiply HM3 by sigmoid((u_sk - T_soft) / scale).
    Provides extra signal in low-u_sk region. Only after F1 if needed.

F3. Per-row instead of Frobenius weighting:
    u_X = raw_X / mean_row_F2_X (= raw_X / (F2_X / N_X))
    Equivalent to a re-scaled c-weighting. Probably not worth a separate
    variant unless F1+F2 fail.

F4. Stiefel rank-2 lift (the §9 escape from prior context). High effort,
    requires reworking the streaming wiring. Defer indefinitely; only
    pursue if scalar-per-v variants S6/S7/... all fail T3 acceptance.
