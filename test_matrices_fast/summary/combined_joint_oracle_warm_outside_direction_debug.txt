Combined objective outside-direction debug handoff
=================================================

Date: 2026-04-19

Purpose
-------
This note records the current debugging state for the combined objective on the
static-cex first block. The immediate question was whether the combined
objective still steers away from the oracle span even when using
--joint-warm-start-oracle, and if so, which outside direction it prefers.


Primary run of interest
-----------------------
Command:

  python cex_restricted_space_probe.py \
    --matrix static-cex --n 128 --rank 2 --win 32 \
    --preset fast --seed 0 \
    --score-variant combined \
    --no-oracle-candidate-check \
    --dump-oracle-old-row-responses \
    --dump-oracle-old-row-response-block 1 \
    --joint-warm-start-oracle

Important note:

  For static-cex, --preset changes optimizer settings, not the generated
  matrix. The first-block matrix is therefore the same as the earlier
  n=128 static-cex probes with seed 0 and v_type=rand. The fast preset plus
  --joint-warm-start-oracle gives a much better optimizer solve than the
  earlier small/optimizer-only reproduction.

Current hypothesis
------------------
The oracle projected directions are strong in the first block, but the two raw
projected oracle directions have nontrivial overlap (~0.2400). The combined
objective is an additive per-vector score with an entropy correction. QR
orthogonalization makes the oracle candidate feasible but hurts the second
vector's entropy/score.

The objective can improve by rotating the second selected vector outside the
oracle QR span. In the oracle-warm fast run, that outside component points
mostly toward global exact tail direction v3, driven by original row 1 appearing
in the first block. Original row 9 also contributes but is much smaller.

This means the oracle-warm optimizer is not simply failing to contain the
oracle span. It is being steered by the combined objective toward a feasible
span that is close to oracle but includes a significant outside/tail component,
especially in the second vector.


Suggested next checks
---------------------
1. Add a first-block diagnostic to cex_restricted_space_probe.py that reports
   each V_score column's outside norm relative to Q_oracle and the top exact
   coordinates of that outside component.

2. Sweep row shuffles/seeds and check whether failures correlate with early
   blocks containing original row 1 or other large tail rows.

3. Compare the current additive per-column combined objective with a subspace
   objective that scores the rank-2 span jointly. This would test whether the
   non-oracle preference is an artifact of per-vector entropy scoring under
   orthogonality.

4. Add an objective-gradient diagnostic at Q_oracle. If the outside tangent
   gradient is nonzero and points to v3/row 1, then oracle QR is not even a
   local stationary point of the current combined objective.
