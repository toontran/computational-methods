Rotation handoff diagnostic: mixed-tail-sharp vs static-cex
===========================================================

Date: 2026-04-22

Question
--------
Now that the second-slot path dependence is known, inspect how the tails take
the place of oracle directions and how the selected frame is rotated before it
is carried as the next sketch. Compare the failing `mixed-tail-sharp` case to
the successful `static-cex` control.


Diagnostic
----------
Added:

  rotation_handoff_diagnostic.py

Raw output:

  summary/rotation_handoff_mixed_static_raw.txt

For each block, the diagnostic compares:

  V_sel:
    optimizer-selected rank-2 frame before handoff compression.

  V_car:
    right basis carried after `left_projected_operator_svd_factors(V_sel.T, M_gain)`.

  Q_oracle:
    projected QR oracle frame for the current block.

Measures:

  sel_oracle_cos:
    principal cosines between V_sel and Q_oracle.

  car_oracle_cos:
    principal cosines between V_car and Q_oracle.

  sel_car_cos:
    principal cosines between V_sel and V_car. This tells whether handoff
    compression changes the retained subspace.

  sel_to_car:
    flattened absolute 2x2 matrix |V_sel' V_car|. This tells whether the handoff
    SVD rotates the basis inside the selected subspace.

  oracle_coords_sel:
    flattened absolute 2x2 matrix |Q_oracle' V_sel|.

  oracle_coords_car:
    flattened absolute 2x2 matrix |Q_oracle' V_car|.

  prev_car_v2_in_sel:
    projection of the previous carried second direction into the current
    selected frame.

  prev_car_v2_dot_sel2:
    direct alignment between previous carried v2 and current selected v2.


Headline
--------
The handoff SVD is not the main source of subspace loss. `sel_car_cos` is nearly
1 throughout both matrices, so the carried basis stays in essentially the same
rank-2 subspace selected by the optimizer.

The important rotation is mostly an in-subspace basis rotation:

  - the optimizer has already selected a rank-2 subspace where one slot is
    tail-biased or missing oracle-2;
  - `left_projected_operator_svd_factors` rotates the two basis vectors inside
    that selected subspace to carry singular directions of the left-projected
    operator;
  - because oracle-2 is not present with enough strength in mixed-tail-sharp,
    the rotation cannot recover it and instead carries an oracle-1/tail mixture;
  - in static-cex, the selected subspace already contains both oracle directions
    sufficiently well, so the same handoff rotation is harmless and eventually
    resolves into the oracle frame.

Conclusion
----------
The tails take the place of oracle directions before handoff compression. The
handoff SVD then rotates the basis inside the selected subspace and carries the
dominant right singular directions of the left-projected operator.

For mixed-tail-sharp:

  - V_sel is already missing a strong oracle-2 component.
  - V_car stays in essentially the same subspace as V_sel.
  - the SVD handoff rotates/mixes basis columns early, but cannot recover
    oracle-2 because oracle-2 is not strongly present in the selected subspace.
  - the carried second slot survives and reinforces a tail-biased complement.

For static-cex:

  - V_sel is also tail-heavy early, and the handoff SVD also rotates columns.
  - however, V_sel contains both oracle directions with much higher early
    overlap.
  - the same in-subspace rotation is harmless because the selected subspace is
    oracle-rich enough.
  - over time both selected and carried frames converge to the oracle span.

Therefore the rotation mechanism is not "handoff SVD rotates a good oracle
subspace away." The failure is earlier: the optimizer gives the second slot to a
tail/high-entropy/high-gain direction. Handoff compression then faithfully
carries and rotates that already wrong rank-2 subspace, creating path-dependent
reinforcement.
