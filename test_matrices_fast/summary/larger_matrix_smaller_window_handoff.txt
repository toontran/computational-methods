Headline: static-cex combined win is a small-window-ratio phenomenon
-------------------------------------------------------------------
static-cex top-1 mean_align (combined / isvd / fd):

  n=128  win=32  (1/4):   0.982 / 0.141 / 0.199   combined huge win
  n=512  win=64  (1/8):   0.063 / 0.063 / 0.089   tied
  n=512  win=32  (1/16):  0.987 / 0.063 / 0.077   combined huge win
  n=1024 win=128 (1/8):   0.045 / 0.045 / 0.045   tied
  n=1024 win=64  (1/16):  0.045 / 0.045 / 0.045   tied
  n=1024 win=32  (1/32):  0.992 / 0.045 / 0.045   combined huge win

Pattern: combined's static-cex advantage disappears at win/n = 1/8 and
reappears strongly at win/n <= 1/16. It is also stable at those ratios across
n: 0.163 (n=512, 1/16) and 0.124 (n=1024, 1/32) are both in the same regime.
This is the opposite of what you would get from a method that merely benefits
from more rows per block; the combined objective specifically helps when each
block sees a small fraction of the matrix rows.

Relative-error-singular-value on static-cex is essentially identical across
combined and isvd (~1e-3) in all configurations; fd's sval shrinkage remains
huge (~0.8-0.95). So the static-cex difference is a subspace-selection effect,
not a sval-accuracy effect.

Takeaways vs prior handoff
--------------------------
1. The static-cex "combined beats PCA" finding from the small n=128, win=32
   benchmark is NOT brittle to n. It IS sensitive to win/n. At ratio 1/8 the
   advantage vanishes; at 1/16 and 1/32 it returns at full strength.
   Interpretation: the combined objective pays off in the "many short blocks"
   regime, which is the deployment regime of interest.

2. Question 2 in the prior handoff ("Does the static-CEX advantage grow with
   n under true random row blocks?") answered: the advantage does not need
   larger n to appear; it needs smaller win/n. It is of the same order at
   n=128 1/4, n=512 1/16, and n=1024 1/32.

3. Question 3 (risk-residual-panel): combined ties or slightly beats iSVD at
   small win/n. The regression with n=1024 (to ~0.82) is a separate issue
   unrelated to the combined-vs-iSVD comparison; both methods regress. A
   rank-2 subspace metric is probably needed here before deciding if this is
   an objective mismatch or a metric artifact.

4. Question 4 (old memory exactly win vs a multiple): not exercised here;
   kept old_memory_size=win throughout.

4. Investigate the risk-residual-panel n=1024 regression separately: both
   methods go from ~0.5 at n=512 to ~0.82 at n=1024, so this is a matrix
   property (or benchmark parameter interaction) rather than a method issue.


Oracle-greedy diagnostic on large-win failure cases
---------------------------------------------------
To answer "is combined failing because the optimizer is stuck, or because
the combined objective itself prefers the bad subspace at large win?", we
added a `greedy-oracle` method to run_joint_warmstart_benchmarks.py. It is
greedy-medium plus oracle_candidate_check=True: after the optimizer picks a
V_score block, the code constructs a candidate V from the projected V_exact
span and replaces the pick iff the oracle candidate has a strictly higher
combined-score sum. This is a proper oracle probe of the greedy step.

Configs tested (the win/n >= 1/8 "failure" regime for combined on static-cex):

  n=512  win=64   (1/8)
  n=1024 win=128  (1/8)
  n=1024 win=64   (1/16, boundary case)

Matrices: static-cex, risk-residual-panel.

Result — greedy-oracle produced identical numbers to greedy-medium on every
(matrix, config) pair, to 6 sigfigs in align and 8 sigfigs in relerr:

  static-cex, n=512  win=64:   0.997980 / 0.00101731  (both methods)
  static-cex, n=1024 win=128:  0.998993 / 0.00101058  (both methods)
  static-cex, n=1024 win=64:   0.998993 / 0.00101082  (both methods)
  risk-resid, n=512  win=64:   0.480630 / 0.02716691  (both methods)
  risk-resid, n=1024 win=128:  0.817619 / 0.04654135  (both methods)
  risk-resid, n=1024 win=64:   0.850441 / 0.04903815  (both methods)

Raw outputs: larger_sweep_results/oracle_*.txt.

Interpretation
--------------
The oracle candidate was NEVER accepted (otherwise numbers would differ).
That is, the combined-objective optimum at these configurations IS near the
iSVD-like / bad subspace — the oracle subspace does NOT achieve a higher
combined score than what plain greedy already finds. Failure is at the
objective level, not the optimizer level.

Why combined's advantage collapses as win/n grows:
- At small win/n (1/16, 1/32), each block sees few rows, so the within-block
  SVD term is weakly identifying. The entropy-over-old-rows term in the
  combined score has real leverage and can push the pick toward the global
  subspace, away from what a per-block SVD would choose.
- At large win/n (1/8+), each block sees enough rows that its local SVD
  already resolves the rank-r subspace well. The combined score is dominated
  by the within-block term and its argmax coincides with the iSVD pick. The
  entropy term can no longer move the optimum.

Implication: combined is not a "better optimizer for the same target as
iSVD"; it is a different objective that agrees with iSVD in the data-rich
per-block regime and differs in the data-poor per-block regime where
retaining old-row information actually matters. Improving combined in the
large-win regime requires changing the objective (or the old-row memory
weighting), not improving greedy.

Followups that would resolve remaining ambiguity
- Re-check with an oracle-weighted combined score that up-weights the
  entropy/old-memory term at large win, to see if an objective tweak can
  recover an oracle-preferred subspace.
- Add the rank-r subspace metric: it is possible the top-1 align 0.999 /
  0.998 values at large-win are both "close to the correct subspace" from
  the rank-2 perspective, in which case there is nothing to recover and the
  large-win regime is simply not a problem to solve.
