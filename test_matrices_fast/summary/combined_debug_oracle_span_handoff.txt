Combined debug oracle-span handoff
==================================

Date: 2026-04-19

Purpose
-------
This note records the current state of debugging combined mode in
cex_restricted_space_probe.py. The key issue is now isolated to the first-block
rank-2 span selection: the oracle projected top-2 span is feasible and gives
the expected near-one final alignment when accepted, but the deployable
optimizer-only combined path still misses it.


Implemented debug workflow
--------------------------
cex_restricted_space_probe.py now has:

  --debug-mode combined

This bundled mode:

  - selects --mode combined by default unless --mode is explicitly passed;
  - selects --score-variant combined by default unless --score-variant is
    explicitly passed;
  - enables oracle candidate checks unless --no-oracle-candidate-check is
    explicitly passed;
  - enables score-component dumps;
  - enables oracle old-row response dumps for every block.

The older flag

  --dump-oldcorrected-score-components

is kept as a compatibility alias for the generic

  --dump-score-components

The component dump now supports both oldcorrected and combined. For combined it
prints gain2, pooled entropy terms, current-window terms, old-row-memory terms,
rows_entropy, rows_seen, and combined_c.

Current diagnosis
-----------------
The passing behavior is established for the debug/oracle-control variant.
The remaining deployable failure is in optimizer-only rank-2 selection.

Important facts:

  - The first-block oracle projected QR frame is feasible and has higher score
    than the greedy optimizer frame in the failing run.

  - Replacing with the oracle candidate in the first blocks gives near-perfect
    oracle-span containment and near-one final mean_align.

  - Adding oracle warm starts alone is not sufficient, because they are first
    projected into the current reduced basis and then optimized under the
    current search/objective path.

  - High-budget joint optimization improves first-block overlap, but still
    does not reliably produce final mean_align near one. It can even select a
    higher combined objective than the oracle QR frame while remaining
    meaningfully rotated away from the oracle span.

Likely next debugging target:

  Determine whether combined score objective itself prefers a non-oracle span,
  or whether the optimizer/reduced-basis expansion is still failing to solve
  the intended rank-2 problem. The first block of the n=128 run is the cleanest
  place to investigate.


Suggested next steps
--------------------
1. Add a first-block oracle-overlap pass/fail line under --debug-mode combined,
   for example requiring both principal cosines against Q_oracle to exceed a
   threshold such as 0.99.

2. For the first n=128 block only, evaluate the combined objective over
   rotations inside span(Q_oracle) and compare it to the best joint optimizer
   span. This will separate basis-dependent score effects from pure search
   failure.

3. Add a diagnostic that reports the best optimizer frame's principal vectors
   relative to Q_oracle, not only the cosines, so the direction of the miss is
   visible.

4. Consider adding Q_oracle directly to the reduced basis as a debug-only
   search-subspace expansion, distinct from the current oracle warm start. This
   would test whether reduced-basis containment is the blocker.

5. Keep --no-oracle-candidate-check runs as the optimizer-only reproduction and
   --debug-mode combined without that flag as the oracle-control/pass run.
