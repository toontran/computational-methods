Score-family workflow
======================

Date: 2026-04-28
Companion to: score_design_overview.txt, diagnostic_toolkit.txt

A "family" = one structural hypothesis about the slot-2/slot-r score
(e.g. rank-r lift, carry-confidence multiplier, soft gate). Variants
inside a family tune that hypothesis. Each family gets its own folder
under summary/ and runs through the steps below.


1. Folder layout
----------------

  summary/score_family_<name>/
    00_known_vs_unknown.md          # 1-pager: settled / open / toolkit gaps
    01_family_design.md             # the family + variant table
    02_gradient_theory.md           # shared ascent / Stiefel infra
    baseline/                       # frozen reference outputs (S6 etc.)
    variants/<variant_name>/
      spec.md                       # exact score, hyperparams, prediction
      diagnostics/                  # T1 grad-check, T2 per-block
      bench/                        # T3 streaming bench
      synthesis.md                  # ship / iterate / kill
    03_cross_variant_synthesis.md   # written after the round closes


2. Step order (per family)
---------------------------

  (1) Current understandings — pin in 00_known_vs_unknown.md from the two
      overview files. Don't re-dump; reference and summarize.
  (2) Lack of understandings — list with the diagnostic that would resolve
      each (Q1..Q6 in score_design_overview.txt §7, gaps a..j in
      diagnostic_toolkit.txt §8).
  (3) New family idea — one structural hypothesis. Write 01_family_design.md
      with the variant table BEFORE coding.
  (4) Variants within the family — adjustments to the hypothesis. Each gets
      a spec.md with exact score + prediction.
  (5) Gradient ascent theory — shared infrastructure in 02_gradient_theory.md
      (tangent projection, retraction, FD check). Build ONCE, variants plug in.
  (6) Implement scores — per variant, on top of the shared infra.
  (7) Benchmarks and component diagnostics — T1 (grad), T2 (per-block),
      T3 (streaming). Diff against baseline/ to "notice changes."
  (8) Further understandings — write 03_cross_variant_synthesis.md and
      update score_design_overview.txt §7 with Q-resolved/refuted pointers.


3. Discipline rules
-------------------

  - Snapshot a frozen baseline into baseline/ before launching variants.
    Otherwise "notice changes" has no reference.
  - Build the gradient infra once, before parallel variant work.
    Otherwise each variant re-derives subtly-different grads.
  - Parallel agents on variants only if specs are frozen and independent.
    Centralize the proposal step; parallelize implementation.
  - Each variant ends with a kill/ship/iterate decision in its synthesis.md.
    No open-ended variants left dangling.
  - When the family closes, append a one-liner to score_design_overview.txt
    §7 marking the Q resolved/refuted, with a pointer to the family folder.
    Otherwise the overview drifts from the actual state of the world.


4. Acceptance bar (inherits from diagnostic_toolkit.txt)
---------------------------------------------------------

  T1 grad-check:  rel_err < 1e-7 at float64
  T2 per-block:   oracle ranks above hm_triplet_raw on every probed block
  T3 streaming:   cos[1]² ≥ 0.6 on static-cex AND mixed-tail-sharp;
                  ≥ 0.7 on diffuse-diffuse; tail_mass ≤ 0.5 on ≥2 of 3
  Operational:    match-or-beat future_hmean_online on the §6 table of
                  score_design_overview.txt (the strict T3 bar above is
                  the MINIMUM; online clears it comfortably on the
                  3-matrix gauntlet). A variant that clears T3 but
                  trails online by 0.3+ on cos1² has not closed the
                  real gap.


5. Backlog (snapshot 2026-04-28)
---------------------------------

Each item has: priority (P0–P3), effort (S/M/L), status (open / blocked /
in-progress / done / killed), depends-on (other backlog ids), resolves
(Q-numbers from score_design_overview.txt §7 / silent assumptions from
§2bis / toolkit §8 gaps), acceptance (the kill/ship criterion). Pick the
highest-priority unblocked item. Multiple agents can pull in parallel
when items have no dependency overlap.

Priority key:
  P0  do now — high value, unblocked, cheap or in critical path
  P1  next  — high value but blocked OR medium cost
  P2  later — moderate value or supporting item
  P3  parking lot — low yield given current evidence; revisit on signal

Status key:
  open         — ready to pick up
  blocked      — waiting on dependency
  in-progress  — assigned/being worked
  done         — closed; pointer in Notes
  killed       — closed without shipping; failure mechanism in Notes

6. Family handoff checklist
----------------------------

When a family closes (kill OR ship):
  - 03_cross_variant_synthesis.md written, includes T1/T2/T3 numbers
    diff'd against baseline/.
  - score_design_overview.txt §7 updated: mark each Q resolved /
    refuted / iterated, with a pointer to the family folder.
  - diagnostic_toolkit.txt §8 updated: any new infra built (subspace
    metric, Stiefel FD, etc.) becomes a permanent toolkit entry.
  - If the family killed a hypothesis (e.g. "rank-r lift doesn't shrink
    plateau"), add a §1bis-style entry to score_design_overview.txt
    documenting the verified failure mechanism so the next family
    doesn't re-do the same probe.
