Score-family workflow and backlog
=================================

Date: 2026-04-28
Companion to: score_design_overview.txt, diagnostic_toolkit.txt

This file owns both the score-family workflow and the active backlog. The
backlog starts in §5; completed items must still propagate their conclusions
back to the overview and toolkit.

A "family" = one structural hypothesis about the slot-2/slot-r score
(e.g. rank-r lift, carry-confidence multiplier, soft gate). Variants
inside a family tune that hypothesis. Each family gets its own folder
under summary/ and runs through the steps below.


1. Folder layout
----------------

  summary/score_family_<name>/
    00_known_vs_unknown.md          # 1-pager: settled / open / toolkit gaps
    01_family_design.md             # the family + variant table
    02_gradient_theory.md           # shared ascent / Stiefel infra
    baseline/                       # frozen reference outputs (S6 etc.)
    variants/<variant_name>/
      spec.md                       # exact score, hyperparams, prediction
      diagnostics/                  # T1 grad-check, T2 per-block
      bench/                        # T3 streaming bench
      synthesis.md                  # ship / iterate / kill
    03_cross_variant_synthesis.md   # written after the round closes


2. Step order (per family)
---------------------------

  (1) Current understandings — pin in 00_known_vs_unknown.md from the two
      overview files. Don't re-dump; reference and summarize.
  (2) Lack of understandings — list with the diagnostic that would resolve
      each (Q1..Q6 in score_design_overview.txt §7, gaps a..j in
      diagnostic_toolkit.txt §8).
  (3) New family idea — one structural hypothesis. Write 01_family_design.md
      with the variant table BEFORE coding.
  (4) Variants within the family — adjustments to the hypothesis. Each gets
      a spec.md with exact score + prediction.
  (5) Gradient ascent theory — shared infrastructure in 02_gradient_theory.md
      (tangent projection, retraction, FD check). Build ONCE, variants plug in.
  (6) Implement scores — per variant, on top of the shared infra.
  (7) Benchmarks and component diagnostics — T1 (grad), T2 (per-block),
      T3 (streaming). Diff against baseline/ to "notice changes."
  (8) Further understandings — write 03_cross_variant_synthesis.md and
      update score_design_overview.txt §7 with Q-resolved/refuted pointers.


3. Discipline rules
-------------------

  - Snapshot a frozen baseline into baseline/ before launching variants.
    Otherwise "notice changes" has no reference.
  - Build the gradient infra once, before parallel variant work.
    Otherwise each variant re-derives subtly-different grads.
  - Parallel agents on variants only if specs are frozen and independent.
    Centralize the proposal step; parallelize implementation.
  - Each variant ends with a kill/ship/iterate decision in its synthesis.md.
    No open-ended variants left dangling.
  - When the family closes, append a one-liner to score_design_overview.txt
    §7 marking the Q resolved/refuted, with a pointer to the family folder.
    Otherwise the overview drifts from the actual state of the world.
  - Any backlog item that resolves, refutes, or creates a fundamental
    open question must propagate that change to the overview docs and
    backlog before it is marked done. The backlog is not just a work
    queue; it is the synchronization point for the story.
  - (2026-04-28) Every new score-design proposal must declare which
    hypothesis it addresses (H1 argmax-shift, H2 landscape-discontinuity,
    H3 slot-1-collapse — see score_design_overview.txt §1quinquies)
    AND state the expected sign of the oracle-vs-winner gap in its
    spec.md BEFORE coding. If the variant ships, the closure must
    report the OBSERVED gap and confirm or refute the expectation.
  - (2026-04-28) "Oracle balance" is not a valid success signal. Audit
    metrics like DIAG-04b ratio_max are descriptive measurements only;
    they cannot be used to decide ship/kill on their own. The Tier-A
    canonical screens (§4) are the decision metrics.


3b. Cross-document propagation policy
--------------------------------------

This applies to EVERY backlog item: families, ablations, infrastructure,
diagnostics, and theory/modeling tasks. If the item changes the current
understanding, its closure must update the main documents in the same
patch / handoff.

Required propagation:

  - score_design_overview.txt
      Update the main story when the item changes an assumption, theory
      status, regime classification, failure mechanism, or open Q. If a
      Q is answered, mark it resolved / refuted / iterated with a pointer
      to the evidence. If a new fundamental Q appears, add it to §7.

  - diagnostic_toolkit.txt
      Register any new diagnostic, invariant, measurement, output folder,
      or known toolkit gap. If a diagnostic closes a gap, mark that gap
      closed and point to the script / synthesis.

  - score_family_workflow.txt
      Update item status, priority, dependencies, acceptance criteria,
      notes, and the current sequencing recommendation. If the item
      invalidates another backlog item's acceptance criterion, rewrite
      that criterion immediately rather than leaving a stale target.

Specific triggers:

  - answers a Q              → mark the Q resolved/refuted/iterated and
                               cite the synthesis or output path.
  - creates a fundamental Q  → add the Q to the overview and add or
                               modify backlog work to answer it.
  - invalidates a criterion  → rewrite the affected acceptance criteria.
  - changes priority/order   → update the sequencing section.
  - adds a diagnostic        → register it in the toolkit.
  - kills a hypothesis       → document the verified failure mechanism so
                               future work does not repeat the same test.

Done means code/bench/synthesis plus propagation. An item with stale
overview, toolkit, or backlog references is not done.


4. Acceptance bar (inherits from diagnostic_toolkit.txt)
---------------------------------------------------------

OVERRIDING PRINCIPLE (2026-04-28, score_design_overview.txt §1quinquies):
"oracle balance" is no longer a decision metric. The acceptance bar is
"oracle identifiability" — does the score's argmax coincide with the
oracle? The Tier-A screens below are mandatory; T1/T2/T3/Operational
are still required but are NOT alone sufficient.

  Tier-A — oracle identifiability (mandatory; new 2026-04-28):
    S-1 vector-level oracle-vs-winner gap:
        Δ_score(winner − oracle_v2_proj) ≤ S6_baseline_Δ + tolerance
        on every §6 matrix at b31. If S6 satisfies this and the new
        variant does not, the variant has moved the argmax off the
        oracle and is REJECTED before any T3 work.
        Tool: `probe_e2_landscape.py`.
    S-2 frame-level oracle-vs-winner gap (FAM-01-DIAG):
        Score(Z_oracle) ≥ Score(Z_winner) on Stiefel(d, r) for
        rank-r ship candidates. The definitive screen.
        Tool: FAM-01-DIAG (under construction).
    S-3 row-cheat dominance:
        Score(Z_oracle) ≥ Score(Z_rowcheat) at b31 on every §6 matrix.
        Already part of the per-block diagnostic.
    S-4 force-oracle ceiling probes:
        Run `--force-oracle-v2` and `--force-oracle-frame` to
        characterize the cos² ceiling and isolate reachability vs
        streaming-state divergence.
        Tool: `half_window_sliding_hmean_experiment.py` flags;
        `run_bench_sweep_force_oracle{,_frame}.sh`.
    S-5 anchor sensitivity:
        Run rank-1 slot-2 optimization in B_def(oracle_v1_proj) AND
        in B_def(slot-1 winner). If one recovers the oracle and the
        other doesn't, the failure is greedy-anchoring. If neither
        does, the evidence model is insufficient.

  Tier-B — Tx legacy (still required, but only after Tier-A passes):
    T1 grad-check:  rel_err < 1e-7 at float64
    T2 per-block:   oracle ranks above hm_triplet_raw on every probed block
    T3 streaming:   cos[1]² ≥ 0.6 on static-cex AND mixed-tail-sharp;
                    ≥ 0.7 on diffuse-diffuse; tail_mass ≤ 0.5 on ≥2 of 3
  Operational:    match-or-beat future_hmean_online (VALUE-ONLY rerun;
                  see INFRA-10) on the §6 table of score_design_overview.
                  txt (the strict T3 bar above is the MINIMUM; online
                  clears it comfortably on the 3-matrix gauntlet). A
                  variant that clears T3 but trails value-only online by
                  0.3+ on cos1² has not closed the real gap.

                  REGIME NOTE (2026-04-28, under §1ter of
                  score_design_overview.txt). The strict 3-matrix T3 bar
                  (static-cex, mixed-tail-sharp, diffuse-diffuse) and the
                  operational §6 table both sit in the HIGH-sample-
                  entropy regime — the score family's home turf where it
                  must be competent on its own merits. The LOW-sample-
                  entropy regime (risk-residual-panel) is conceded to
                  iSVD/SVD by the complementarity plan and is NOT in the
                  ship-criterion: variants are expected to be competitive
                  there but not to beat iSVD. DIAG-01 corrected
                  residual-spiky-shocks to BOUNDARY because oracle slot-1
                  is low-support while oracle slot-2 is moderate-support;
                  use it as a mixed-case audit point, not a primary ship
                  criterion. Acceptance criteria that reference iSVD on
                  the low-entropy regime should be rewritten as stretch
                  goals (see FAM-02 below).

                  NOTE (2026-04-28, FB-001 propagation): the operational
                  "online" baseline is `future_hmean_online` evaluated
                  with the value-only candidate pool. Numbers and
                  artifact paths live at
                  summary/bench_matrix_sweep_value_only_online/
                  (synthesis.txt; INFRA-10). The original oracle-aware
                  pool (adds `q2_vs_q1oracle` = V_exact[:,1] projected
                  into the row span; --online-include-oracle restores

5. Backlog (snapshot 2026-04-28)
---------------------------------

Each item has: priority (P0–P3), effort (S/M/L), status (open / blocked /
in-progress / done / killed), depends-on (other backlog ids), resolves
(Q-numbers from score_design_overview.txt §7 / silent assumptions from
§2bis / toolkit §8 gaps), acceptance (the kill/ship criterion). Pick the
highest-priority unblocked item. Multiple agents can pull in parallel
when items have no dependency overlap.

Priority key:
  P0  do now — high value, unblocked, cheap or in critical path
  P1  next  — high value but blocked OR medium cost
  P2  later — moderate value or supporting item
  P3  parking lot — low yield given current evidence; revisit on signal

Status key:
  open         — ready to pick up
  blocked      — waiting on dependency
  in-progress  — assigned/being worked
  done         — closed; pointer in Notes
  partial      — partial-pass; a subset of the §6 suite is still a
                 live ship candidate, the rest is killed/redirected.
                 Use when an item passes some matrices and fails
                 others; Notes must list the per-matrix verdict.
  killed       — closed without shipping; failure mechanism in Notes

Closure / kill principle (revised 2026-04-28 after FAM-01-DIAG re-read):
  Any S-2 rank-r ship gate uses the TWO-PART rule defined in
  score_design_overview.txt §1quinquies — alignment (operational) +
  Δ_score (diagnostic). Do NOT close an item as `killed` when the
  score's argmax is operationally aligned with the oracle subspace
  (pa_cos²[0] ≥ 0.9 and min pa_cos² ≥ τ_align): that's
  PASS-with-overshoot, ship-eligible. Do NOT close as `done` when
  Δ_score ≤ 0 but pa_cos² is poor: that's a score that "matches
  oracle in value" while pointing at the wrong subspace (artifact of
  the score, not evidence). Verdict labels in Notes must use the
  canonical S-2 set:
    PASS-aligned, PASS-with-overshoot, FAIL-slot-r-only, FAIL-subspace.
  Items with mixed verdicts close as `partial` with the per-matrix
  table in Notes.
