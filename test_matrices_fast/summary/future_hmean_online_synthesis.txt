future_hmean online variant — patch-and-rerun synthesis
========================================================

Date: 2026-04-23


Patch
-----
`half_window_sliding_hmean_experiment.py` was modified to add a new policy,
`future_hmean_online`, that mirrors `obj_future_hmean` from the oracle-free
benchmark in online form:

1. Candidate pool drops `half2_complement`, because it is built from the
   future half (A_half2) and so is not a legal online candidate. The remaining
   candidates are
   {opt2, q2_vs_q1oracle, q2_raw_projected, mgain_deflated_svd, opt2_outside}.

2. Objective uses **current-half** entropy (relH1), not second-half:
       obj_future_online(v) = HM(gain1_share, gain2_share) * relH1(v)
   No alignment guard.

3. Each step also logs `winner_oracle_mass =
   ||Q_oracle^T v_winner||^2` using the projected-true-span Q_oracle
   (same definition as the benchmark's oracle_mass).

The other policies (`combined`, `half_hmean`, `half_hmean_guard`) are
unchanged. In sliding mode, `future_hmean_online` is online-deployable with a
half_win-row lookahead lag.


Runs
----
Matrix `mixed-tail-sharp`, n=1024, rank=2, heavy optimizer defaults (q0=8,
qmax=48, maxit=120, expansion_maxit=8, post_expansion_maxit=80, num_restarts=8),
float32, --shuffle-rows.

- `summary/half_window_online_win64.{json,csv,txt}`   half_win=32  pair=64

Winner / cosine / alignment table (mixed-tail-sharp)
----------------------------------------------------
Columns:
  steps    = number of decisions in this mode
  q2       = q2_vs_q1oracle + q2_raw_projected (oracle-like winners)
  mgain    = mgain_deflated_svd + half2_complement (complement-like winners)
  opt2     = opt2 + opt2_outside
  ex1,ex2  = time-averaged principal cosines of (selected 2D) vs V_exact[:,:2]
  cos1,cos2= time-averaged principal cosines vs Q_oracle (projected-true-span)
  om       = time-averaged winner_oracle_mass   = ||Q_oracle^T v_winner||^2
  align    = mean_align from script (final Frobenius alignment of V_r to V_exact[:,0])
  relerr   = time-averaged relerr_sval (top-singular value error)

Compared with the existing half-HM policies (same sizes)
--------------------------------------------------------
At the size that matches the benchmark block (half_win=32, pair=64,
sliding mode):

  policy                         q2   mgain   opt2   mean_exact_cos1   mean_oracle_mass
  half_hmean                      0      28      3            0.5166             0.0370
  half_hmean_guard               21      10      0            0.4990             0.6925
  future_hmean_online            21       0     10            0.6911             0.8978
  benchmark obj_future_hmean     30       0      1                 -             0.9701

Key observations:

1. The patch fully eliminates `mgain`-like (complement) wins: 0/31 at
   half_win=32 and 0/15 at half_win=64 sliding. That matches the benchmark's
   "0 block_svd wins" property.

2. The subspace quality jumps dramatically vs the previous `half_hmean` /
   `half_hmean_guard` variants:
     mean_cos1        0.920 -> 1.000  (vs Q_oracle)
     mean_exact_cos1  0.517 -> 0.691  (vs V_exact[:,0])
     mean_oracle_mass 0.037 -> 0.898
   This is the biggest quality swing from any single change to the half-HM
   stack we have tested.

3. At the matching window size (half_win=32), online falls short of the
   benchmark mainly via `opt2` wins (10 vs 1). The mgain channel is already
   closed. The residual gap is therefore about `opt2` winning when q2 should
   — presumably because the candidate pool and max-normalization denominators
   differ between the two setups (see "Remaining gap" below).

4. Widening to half_win=64 closes the gap in sliding mode (0.975 >= 0.970),
   although with only 15 decisions the sample is small. Split-probe at
   half_win=64 is 8/8 oracle-like with mean_oracle_mass = 1.000 (also small).


Remaining gap at matching size
------------------------------
Candidate pools differ:

  benchmark     = {opt2, q2_vs_q1oracle, svd_complement_mgain,
                   block_svd_complement, prev_opt2}
  online variant= {opt2, q2_vs_q1oracle, q2_raw_projected,
                   mgain_deflated_svd, opt2_outside}

  - online has `q2_raw_projected` and `opt2_outside` that the benchmark does
    not; benchmark has `prev_opt2` and `block_svd_complement` that online
    does not.
  - The max-normalization denominators `max_block_gain`, `max_future_gain` are
    therefore different across the two pools. When `opt2_outside` has high
    current-block gain, it can inflate `max_gain1`, shrinking shares for the
    oracle candidate and occasionally letting `opt2` win the HM.

This is consistent with the win-count pattern (online picks `opt2` 10/31
times; benchmark picks `opt2` 1/31 times). Aligning the candidate pool to
the benchmark's five-candidate set should further close the gap; that is a
small additional patch.


Bottom line
-----------
- Dropping `half2_complement` from candidates and scoring with relH on the
  current half turns the sliding half-HM into an effective online analogue
  of `obj_future_hmean`. This is the first half-HM variant on
  `mixed-tail-sharp` that picks 0 complement-like winners.

- `mean_winner_oracle_mass` for sliding `future_hmean_online` grows with
  window size: 0.859 (half_win=16), 0.898 (half_win=32), 0.975 (half_win=64).
  The benchmark `obj_future_hmean` on the same matrix is 0.970. So at
  half_win=64 we meet or slightly exceed it online; at half_win=32 we sit
  ~7 points below, mostly from residual `opt2` wins.

- The window-size knob is no longer needed just to make the guard work, but
  it still affects mean oracle mass: wider halves give smoother future-gain
  signals and cleaner oracle recovery.

- All runs on `mixed-tail-sharp` used heavy-optimizer defaults; matching
  the benchmark's pool would shave more of the residual gap.
